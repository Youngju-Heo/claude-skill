# 기능 개발 워크플로

모든 개발은 **기획/설계 → 상세계획 → 구현/테스트 → 최종리뷰** 순서로 진행한다.

## 모델·추론 수준 선택

- 기본 모델 계열은 Sol로 한다. 사용자가 다른 모델이나 추론 수준을 명시적으로 요청하면 지정한 작업·단계에 그 설정을 우선 적용한다. 적용 범위가 끝나면 기본 기준으로 돌아간다.
- 사용자 지정이 없으면 다음 단계별 추론 수준을 적용한다. 작업이 쉽거나 어렵다는 판단만으로 임의 변경하지 않는다.

| 작업·단계 | 추론 수준 |
| --- | --- |
| 경량 경로의 수정·탐색·문서 작업 및 관련 검증 | Light |
| 전체 경로의 기획·설계·브레인스토밍 | High |
| 전체 경로의 상세계획 | High |
| 전체 경로의 구현·테스트 작성·검사 실행 | Medium |
| 경로와 무관하게 실패 원인을 분석하는 디버깅 | High |
| 전체 경로의 최종리뷰 | High |

- 디버깅이 끝나면 원래 단계의 수준으로 돌아간다. Extra High 이상과 Astra·Luna 등 다른 모델은 사용자가 요청한 경우에만 적용한다.
- 단계 시작 시 적용할 모델·추론 수준을 짧게 알린다. 현재 대화의 설정을 변경할 도구가 없거나 지정한 설정을 지원하지 않으면, 필요한 설정과 실제 설정의 차이를 알리고 사용자에게 변경을 요청한다. 설정 변경 또는 현재 설정으로 진행하라는 사용자 지시가 있기 전에는 해당 단계의 실행을 보류한다. 자동 전환했다고 말하지 않는다.
- 이 기준을 적용하기 위해 서브에이전트를 임의 생성하지 않는다. 위임은 AGENTS.md 및 사용자가 승인한 범위를 따른다.

## 단계별 실행 규칙

각 단계 시작 시 아래 스킬을 읽고 적용한다. 모델·추론 수준은 위의 Codex 기준을 따른다.

| 단계 | 사용할 스킬 |
| --- | --- |
| 기획/설계 | `superpowers:brainstorming` |
| 상세계획 | `superpowers:writing-plans` |
| 구현/테스트 | `superpowers:subagent-driven-development`, `superpowers:test-driven-development` |
| 최종리뷰 | `superpowers:requesting-code-review` |

- 구현/테스트에서 서브에이전트 위임이 허용되고 독립적인 태스크로 나눌 수 있으면 `superpowers:subagent-driven-development`를 적용한다. 직접 실행하는 경우에는 `superpowers:executing-plans`와 `superpowers:test-driven-development`를 적용한다.
- 스킬의 서브에이전트 사용 지침은 AGENTS.md와 사용자가 허용한 위임 범위 안에서 적용한다. 최종리뷰를 직접 수행하는 경우에도 `superpowers:requesting-code-review`의 리뷰 기준을 따른다.
- 필요한 스킬을 사용할 수 없으면 해당 스킬과 제약을 보고하고 아래 절차를 직접 수행한다. 승인·TDD·리뷰 규칙을 생략하거나 완화하지 않는다.
- 기획/설계에서는 원 요청, 인수 조건, 기존 구조와 대안을 확인한다. 상세계획에는 수정 파일, 작업 순서, 테스트 방법을 작성한다.
- 구현/테스트에서는 버그 재현 테스트를 먼저 작성하고 실패 → 수정 → 통과 순서로 진행한다. 프로젝트 필수 검사와 변경 관련 테스트를 수행하고 실행하지 못한 검사는 이유를 보고한다.
- SDD를 수행하는 경우 태스크별 리뷰는 구현 단계에 속하며 구현 단계의 모델·추론 기준을 따른다. 위임은 사용자가 요청했거나 프로젝트에서 명시적으로 허용한 범위에 한정한다.
- 최종리뷰는 전체 브랜치를 **1회만** 리뷰한다. 추가 리뷰 라운드나 재검증 패스를 스스로 만들지 마라.
- 리뷰에서는 발견한 이슈를 심각도와 무관하게 모두 보고하라.
- 최종리뷰에는 산출물이 「원 요청」 인용문에 어떻게 답하는지를 계획 준수 여부와 독립된 별도 항목으로 서술한 뒤 판정하라.
- 위 단계에 정의된 것 외의 서브에이전트는 만들지 마라.

## 단계 전환 규칙

- 기획/설계와 상세계획 단계가 끝나면 산출물(설계 문서, 계획 문서)을 요약해 보고하고
  사용자 컨펌을 받은 뒤에만 다음 단계로 진행하라.
  컨펌 없이 다음 단계를 시작하지 마라. 수정 요청이 있으면 반영 후 다시 컨펌을 받아라.
- 컨펌 보고에는 「원 요청」 인용과, 산출물이 그 요청에 어떻게 답하는지를 함께 제시하라.
  사용자가 승인하는 대상은 산출물 자체가 아니라 "원 요청에 대한 답"이다.
- 구현/테스트가 끝나면 컨펌 없이 바로 최종리뷰로 진행하라.
- 최종리뷰가 끝나면 구현 결과와 리뷰에서 발견된 이슈를 함께 보고하고 사용자 컨펌을 받아라.
  이 컨펌이 머지·이슈 수정 여부의 결정이다.

## 경량 경로

아래 두 조건을 **모두** 만족하면 4단계 대신 경량 경로를 쓴다.

- 설계 결정이 없다 — 어떻게 고칠지가 자명하고 선택지가 하나뿐이다.
- 변경이 한 관심사에 국한된다 — 새 모듈·새 의존성·인터페이스 변경이 없다.

경량 경로:

1. 무엇을 왜 어떻게 고칠지 2~3줄로 보고하고 컨펌을 받아라.
2. 구현하라. 버그면 재현 테스트를 먼저 쓴다(TDD는 그대로 유지한다).
3. 변경 요약을 보고하라. 설계·계획 문서와 최종리뷰는 생략한다.

- 판단이 애매하면 전체 경로를 써라. 경량 경로는 예외이지 기본값이 아니다.
- 구현 중에 설계 결정이 필요해지면 즉시 멈추고 전체 경로로 전환하라.
- 브랜치·커밋 규칙은 경량 경로에도 그대로 적용된다.

## 브랜치·커밋 규칙

- 새 기획 시작 시 `{feature-name}` 기반으로 브랜치를 만들고 시작하라.
- 작업 단계별로 git에 커밋하여 이력을 저장하라.
- **커밋 메시지 형식**: `<type>: #<일감번호> <제목 (한글 가능)>` + 본문(선택)
  - type 예시: `feat`, `fix`, `refactor`, `chore`, `docs`
  - #<일감번호>: DevOps, Zira 등 형상관리 도구에 사용하는 번호가 있을 경우, 없으면 생략
- **`Co-Authored-By` 문구 사용 금지** — 커밋 메시지에 포함하지 않음

## 문서 규칙

- 기획/계획 작성 시 반드시 markdown 파일로 저장하라.
  - 설계: `docs/feature/yyyy-mm/yyyy-mm-dd-{day-sequence}-{feature-name}-design.md`
  - 계획: `docs/feature/yyyy-mm/yyyy-mm-dd-{day-sequence}-{feature-name}-plan.md`
  - `{day-sequence}`는 그날 순번 2자리, `01`부터. 계획은 해당 설계와 동일한 순번을 쓴다.
- 설계·계획 문서 맨 위에 「원 요청」 섹션을 두고 사용자의 요청을 원문 그대로 인용하라(요약·의역 금지).
  계획 문서는 설계 문서의 인용을 그대로 옮긴다.
- 설계 문서에는 해당 기능의 주요 엔티티·모듈 네이밍 항목을 포함하라.
  구현은 이 네이밍을 따른다. (코드 네이밍 상세 규칙은 `.agents/rules/`의 언어별 규칙을 따르라.)
- 문서는 결정 사항과 그 근거 중심으로 필요한 내용만 담아라. 상투적 요약, 채우기 섹션, 중복 설명으로 분량을 늘리지 마라.
- 모든 문서는 한국어로 작성하라.

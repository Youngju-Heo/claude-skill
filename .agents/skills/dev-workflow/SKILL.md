# 개발 워크플로

외부 스킬이나 특정 모델에 의존하지 않고 아래 절차를 직접 수행한다.

## 모델·추론 수준 선택

- 기본 모델 계열은 Sol로 한다. 사용자가 다른 모델이나 추론 수준을 명시적으로 요청하면 지정한 작업·단계에 그 설정을 우선 적용한다. 적용 범위가 끝나면 기본 기준으로 돌아간다.
- 사용자 지정이 없으면 다음 단계별 추론 수준을 적용한다. 작업이 쉽거나 어렵다는 판단만으로 임의 변경하지 않는다.

| 작업·단계 | 추론 수준 |
| --- | --- |
| 경량 경로의 수정·탐색·문서 작업 및 관련 검증 | Light |
| 전체 경로의 기획·설계·브레인스토밍 | High |
| 전체 경로의 상세계획 | High |
| 전체 경로의 구현·테스트 작성·검사 실행 | Medium |
| 경로와 무관하게 실패 원인을 분석하는 디버깅 | High |
| 전체 경로의 최종리뷰 | High |

- 디버깅이 끝나면 원래 단계의 수준으로 돌아간다. Extra High 이상과 Astra·Luna 등 다른 모델은 사용자가 요청한 경우에만 적용한다.
- 단계 시작 시 적용할 모델·추론 수준을 짧게 알린다. 현재 대화의 설정을 변경할 도구가 없거나 지정한 설정을 지원하지 않으면, 필요한 설정과 실제 설정의 차이를 알리고 사용자에게 변경을 요청한다. 설정 변경 또는 현재 설정으로 진행하라는 사용자 지시가 있기 전에는 해당 단계의 실행을 보류한다. 자동 전환했다고 말하지 않는다.
- 이 기준을 적용하기 위해 서브에이전트를 임의 생성하지 않는다. 위임은 AGENTS.md 및 사용자가 승인한 범위를 따른다.

## 작업 시작과 경로 선택

1. 관련 AGENTS.md, 기존 변경, 프로젝트의 빌드·테스트 방법을 확인한다.
2. 사용자의 요청과 성공 기준을 짧게 정리한다. 설계 결정이 없고 한 관심사의 변경이며 새 모듈·의존성·공개 인터페이스 변경이 없으면 경량 경로를 사용한다.
3. 그 밖에는 전체 경로를 사용한다. 조사로 판단 가능한 사항은 먼저 확인하고, 결과를 크게 바꾸는 선택만 사용자에게 묻는다.

## 경량 경로

- 무엇을 왜 고칠지 짧게 알리고 명확히 요청받은 변경은 바로 수행한다.
- 버그는 가능하면 재현 테스트를 먼저 만든다. 오타·문서·상수 등 낮은 영향의 수정에 구현을 그대로 복제하는 테스트를 추가하지 않는다.
- 변경과 관련된 검증을 수행하고 결과와 한계를 보고한다. 별도 설계·계획 문서와 정식 최종리뷰는 생략한다.
- 작업 중 중요한 설계 결정이 생기면 변경을 확대하기 전에 전체 경로로 전환한다.

## 전체 경로

### 1. 기획·설계
- 원 요청, 인수 조건, 기존 구조를 읽고 필요한 대안·트레이드오프를 정리한다.
- 주요 엔티티·모듈 이름, 변경 범위, 호환성, 성공 기준을 설계 문서에 작성한다.
- 문서를 저장하고 원 요청에 어떻게 답하는지 요약해 설계 승인을 받는다. 승인받기 전 구현하지 않는다.

### 2. 상세계획
- 승인된 설계로부터 수정할 파일, 작업 순서, 테스트 방법을 계획 문서에 작성한다.
- 계획을 요약하고 승인받은 뒤 구현한다. 이미 사용자가 해당 산출물이나 단계의 진행을 명시적으로 승인했다면 중복 확인하지 않는다.

### 3. 구현·테스트
- 작은 단위로 구현한다. 동작 변경·버그에는 의미 있는 테스트를 작성하고 가능하면 실패→수정→통과 순서를 따른다.
- 프로젝트 필수 검사와 변경 관련 테스트를 수행한다. 실행할 수 없는 검사는 이유를 기록한다.
- 통과한 검사는 추가 변경, 실패 또는 해결되지 않은 우려가 있을 때만 다시 수행한다.

### 4. 최종리뷰
- 전체 변경을 한 차례 리뷰한다. 정확성·회귀·인수 조건과 함께, 산출물이 원 요청에 어떻게 답하는지를 서술해 판정한다.
- 확인된 결함은 심각도와 무관하게 보고한다. 취향·추측·범위 밖 개선은 결함과 구분한다.
- 요청 범위의 명백한 결함은 수정하고 영향을 받는 검사만 재실행한다. 새 설계 결정이 필요한 수정은 사용자에게 판단을 요청한다.
- 최종 결과, 검사 결과, 미해결 이슈를 보고한다. 새 근거 없이 전체 리뷰 라운드를 반복하지 않는다. 통합 브랜치 머지는 사용자에게 맡긴다.

## 브랜치·커밋

- Git 저장소에서 새 기능을 시작할 때 적절한 작업 브랜치를 사용한다. 기존 작업 브랜치가 있으면 이어 쓰고, 현재 브랜치를 바꾸기 전에 미커밋 변경을 확인한다.
- 새 브랜치의 기본 이름은 `feature-name`, DevOps 경로는 `work-item-id-feature-name`이다. 프로젝트의 브랜치 접두사 규칙이 있으면 우선한다.
- 의미 있는 작업 단계마다 변경을 확인하고 관련 파일만 커밋한다. 사용자 변경을 함께 커밋하지 않는다. 커밋하지 말라는 요청을 우선한다.
- 메시지: `<type>: #<일감번호> <한국어 제목>`. 번호가 없으면 생략하고 Azure Boards와 GitHub 연동이면 `AB#번호`를 쓴다.
- Co-Authored-By를 추가하지 않는다. push·PR·머지는 각각 사용자 요청 범위에 포함되는지 확인한다.

## 문서

- 전체 경로의 설계·계획은 한국어 Markdown으로 저장한다.
- 설계: `docs/feature/yyyy-mm/yyyy-mm-dd-NN-feature-name-design.md`
- 계획: `docs/feature/yyyy-mm/yyyy-mm-dd-NN-feature-name-plan.md`
- 사용자 현지 날짜와 그날의 미사용 2자리 순번을 사용한다. 설계와 계획은 같은 순번을 공유한다. 기존 문서를 덮어쓰지 않는다.
- 문서 상단의 「원 요청」에 사용자 요청을 원문 인용한다. 후속 변경은 별도 기록하고, 외부 일감 설명은 원 요청과 구분한다. 비밀값은 문서에 복제하지 않는다.
- 결정과 근거 중심으로 작성하며 중복 설명과 상투적 섹션으로 분량을 늘리지 않는다.
